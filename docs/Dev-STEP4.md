## 1. 핵심 설계 — LLM 에게 타임스탬프를 묻지 않는다

STEP 4 의 가장 중요한 결정. **문장 번호로 주고받고, 시각은 우리가 채운다.**

```
LLM 에 주는 것            LLM 이 돌려주는 것          우리가 계산
────────────────         ──────────────────        ──────────────
[0] 안녕하세요.           {"label": "주제소개",       t_start = sentences[0].t_start
[1] 오늘 발표를…            "title": "…",             t_end   = sentences[0].t_end
[2] 기존 방식은…             "start": 0, "end": 0}
   (시각 없음)
```

**이유 1 — 환각 차단.** LLM 은 오디오를 측정하는 게 아니라 그럴듯한 토큰을 생성한다.
시각을 직접 받으면 검증 불가능한 값이 섞인다. 우리는 `stt_sentences` 에 **정확한 시각을
이미 갖고 있으므로** 다시 만들어 달라고 할 이유가 없다.

**이유 2 — 기계적 검증이 가능해진다.** 번호는 우리 데이터와 1:1 이라 아래를 전부 확인할 수 있다.
시각을 받으면 "47.3초가 맞는지" 알 방법이 없다.

| 검사 | 보정 |
|---|---|
| 번호 범위 초과 | `0 ~ n-1` 로 클램프 |
| 경계 불연속(빈틈·겹침) | 직전 구간 끝 + 1 로 맞춤 |
| 끝 < 시작 | 시작값으로 맞춤 |
| 마지막 문장 누락 | 끝까지 확장 |
| 목록 밖 라벨 | 경고만, 값은 유지 |

> **전사문에 시각을 넣지 않는 것도 의도적이다.** 보여주면 모델이 흉내 내 시각을
> 출력하려 든다. 번호만 주면 번호만 돌려준다.

## 2. 모듈 구조

```
app/pipeline/step4_segmentation.py
├── LABELS              라벨 목록 (12종)
├── PROMPT              프롬프트 템플릿
├── build_transcript()  문장 → "[i] 텍스트" 번호 매긴 전사문
├── _repair()           LLM 출력 검증·보정
├── _merge_sandwich()   같은 라벨이 되돌아오면 사이를 흡수
├── _merge_short()      부스러기 구간 흡수
└── run()               전체 실행 (재시도 3회)
```

`run(sentences)` 의 입력은 `stt_sentences` 형식(`text` / `t_start` / `t_end`) 그대로다.
STEP 3 결과를 **STT 재실행 없이** 바로 넘길 수 있다.

```python
result = step4_segmentation.run(stt_sentences)
# result.segments[i] → label / title / start_idx / end_idx / t_start / t_end
# result.warnings    → 검증·보정 내역
```

## 3. 라벨 설계

```
인사 · 주제소개 · 배경설명 · 문제제시 · 해결방안 · 시스템구조
구현 · 시연 · 결과 · 한계 · 향후계획 · 결론
```

- **순서를 강제하지 않는다.** 발표마다 흐름이 다르고, 같은 라벨이 여러 번 나와도 된다.
- **목록 밖 라벨을 새로 만들지 못하게** 프롬프트에 못박는다.
- **「기타」는 두지 않는다** — 곁길로 샐 때마다 잘리면 분리가 지나치게 빈번해진다.
  (재검토 대상 → `_refs/Todo-회의필요.md` 3번)

### ⚠️ 17종 → 12종으로 줄인 이유

초기 목록에는 `개념설명 · 고찰 · 선행사례 · 목표 · 마무리` 가 있었다. 이들이 문제였다 —
**독립 구간이 아니라 다른 구간을 설명하려고 곁들이는 것**이라, 남겨두면 하나의 논의가
잘게 부서진다.

실측(137초 발표):
```
개념설명 있을 때 (17종)          개념설명 제거 후 (12종)
─────────────────────           ────────────────────
주제소개  [ 0- 0]  10.5s          주제소개  [ 0- 0]  10.5s
배경설명  [ 1- 2]  22.0s          문제제시  [ 1- 5]  38.0s
문제제시  [ 3- 5]  16.0s          해결방안  [ 6-10]  28.1s
해결방안  [ 6-10]  28.1s          한계     [11-16]  42.8s  ← 4조각이 하나로
한계     [11-13]  14.5s          향후계획  [17-17]  11.9s
개념설명  [14-15]  19.1s
한계     [16-16]   4.5s   ← 한계 논의가
개념설명  [17-17]  11.9s      네 조각으로 쪼개짐
```

## 4. 프롬프트

```
당신은 발표 영상을 분석하는 도우미입니다.
아래는 한 발표의 음성을 문장 단위로 전사한 것입니다.
각 줄 앞의 [숫자]는 문장 번호입니다.

이 발표를 의미 단위 구간으로 나누세요.

1. 문장 번호로만 경계를 지정하세요. 시간(초)은 쓰지 마세요.
2. 구간은 빠짐없이 이어져야 합니다. 첫 구간은 [0]에서 시작하고,
   마지막 구간은 마지막 문장에서 끝나며, 빈 번호나 겹치는 번호가 없어야 합니다.
3. 주제가 바뀌는 지점에서만 자르세요. 이야기가 잠시 곁길로 새는 정도로는
   자르지 말고 직전 구간에 포함시키세요.
4. 어떤 내용을 설명하기 위해 곁들인 이야기(용어 설명, 사례, 부연)는
   독립 구간으로 만들지 마세요. 설명 대상이 속한 구간에 포함시킵니다.
   예: 「한계」를 말하다가 그 한계와 관련된 기술을 설명했다면, 그 설명까지
   전체가 하나의 「한계」입니다. 설명이 끝나고 다시 한계 이야기로 돌아와도
   쪼개지 말고 하나로 두세요.
5. 각 구간에 아래 라벨 중 가장 가까운 것 하나를 고르세요.
   순서는 정해져 있지 않고, 같은 라벨이 여러 번 나와도 됩니다.
   목록에 없는 라벨을 새로 만들지 마세요.
```

출력은 JSON 배열: `[{"label", "title", "start", "end"}, ...]`

| 설정 | 값 | 이유 |
|---|---|---|
| 모델 | `gemini-2.5-flash` | STEP 2 와 동일 |
| `response_mime_type` | `application/json` | 파싱 안정성 |
| `temperature` | `0.2` | 창작이 아니라 분류 작업 |
| 재시도 | 3회 | STEP 2 패턴과 동일 |

### ⚠️ 구간을 크게 만드는 수단은 길이 제약이 아니다

처음엔 "목표 개수"와 "최소 45초" 로 길이를 조였는데, **정상적인 흐름까지 뭉갰다** —
137초 발표가 구간 1~2개로 붕괴하고 좋았던 5단 구조가 사라졌다. 사용자가 원한 구간은
10초·16초·22초짜리도 있었으므로 길이가 문제가 아니었다.

**실제 원인은 라벨 설계였다.** 라벨을 줄이고 흡수 규칙(프롬프트 4번)을 넣자
길이 제약 없이도 원하는 구조가 나왔다.

→ 현재 길이 관련 상수는 **부스러기 제거용으로만** 남아 있다.

## 5. 후처리 (LLM 출력에 의존하지 않는 안전망)

프롬프트가 무시돼도 결과가 무너지지 않도록 두 겹을 둔다. 순서가 중요하다.

```
LLM 출력 → _repair() → _merge_sandwich() → _merge_short() → 시각 매핑
```

**`_merge_sandwich(gap=1)`** — 같은 라벨이 되돌아오면 사이에 낀 구간까지 하나로.
```
한계 → 개념설명 → 한계   ⇒   하나의 «한계»
```
중간에 낀 것은 앞뒤 논의를 설명하려고 곁들인 경우가 대부분이다.
간격을 **1칸으로 제한**한다 — 발표 앞뒤로 멀리 떨어진 동일 라벨까지 합치면 안 된다.

**`_merge_short(5초)`** — 명백한 부스러기만 이웃에 흡수. 라벨·제목은 **긴 쪽**을 따르고,
이웃 중 **더 짧은 쪽**과 합쳐 한쪽만 비대해지는 것을 막는다.

| 상수 | 값 | 역할 |
|---|---|---|
| `MIN_SEGMENT_SEC` | 5.0 | 부스러기 흡수 (정상 흐름은 10초대도 유효) |
| `MAX_SANDWICH_GAP` | 1 | 샌드위치 병합 허용 간격 |

## 6. DB 저장

```
segments
  segment_id   PK
  session_id   FK
  label        분류용 semi-enum — 회차 비교·집계   ← 2026-09-16 추가
  title        사용자에게 보여줄 한 줄 요약
  t_start      LLM 이 아니라 stt_sentences 에서 가져온 값
  t_end
  slide_index  (PDF 업로드 시 슬라이드 매칭 — 미구현)
```

`label` 과 `title` 은 **역할이 다르므로 분리**한다. `label` 로는 *"이번 회차엔 문제제시
구간이 짧았다"* 같은 비교가 가능하고, `title` 은 화면에 그대로 뿌린다.

### 이어지는 집계
STEP 4 는 새로 측정하지 않는다. 구간 시간 범위로 **앞 단계 결과를 잘라 담을 뿐**이다.

```
segments[i] = (t_start, t_end)
      ↓ 이 범위에 걸치는 것을 모아서
segment_analyses[i]
  stt_text               ← stt_sentences 중 범위 안 문장 이어붙임
  speaking_rate_spm      ← 음절 수 ÷ 구간 길이
  articulation_rate_spm  ← 음절 수 ÷ (구간 길이 − 구간 내 무음)
  silence_count          ← voice_raws.silence_segments 중 범위 안 개수
  filler_count           ← voice_raws.filler_words     중 범위 안 개수
  repetition_count       ← voice_raws.repetitions      중 범위 안 개수
  gesture/posture/eye_contact_counts ← video_analyses 중 겹치는 청크 합산
```

세 배열(`silence_segments`·`filler_words`·`repetitions`)이 **같은 뼈대**
(`t_start`/`t_end`/`duration`)라 같은 코드로 처리된다.

## 7. 개발 도구

`/voice/segments` (통합 테스트 서버, 포트 8001)

- **입력 두 가지** — STEP 3 분석 기록 선택(실제 시각) / 직접 텍스트 입력(줄당 3초 가정)
- **구간 막대** — 라벨별 색으로 비율 표시. 같은 라벨은 항상 같은 색(이름 해시)
- **구간별 보기** — 각 구간의 문장을 전부 표시
- **전체 전사문** — 문장 순서대로, 어느 구간인지 왼쪽 색띠로 표시
- **검증 경고** — 보정이 일어났으면 내역 표시

> 테스트 도구는 **DB 를 건드리지 않는다.** 결과는 화면에만 표시된다.
